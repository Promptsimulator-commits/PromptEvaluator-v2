# Spine Pair Review — Prompt Evaluator

> **Resolution status (added after `/bmad-code-review`, 2026-09-08):** This report is a point-in-time snapshot taken before the fixes below landed. Findings 1 (Flow coverage), 2 (contrast ratios / opacity convention), 3 (Status pill component row), 4 (in-flight/error/stale-analysis states), and the "high-severity mechanical inaccuracy" (Layout & Spacing side-by-side claim) in Mechanical notes were **all fixed directly in `DESIGN.md`/`EXPERIENCE.md`** as part of the same pass — see Flow 2, the Opacity/Known-contrast-gaps paragraphs, the Status pill row in Component Patterns, the four new State Patterns rows, and the Layout & Spacing exception clause. Only the Elevation & Depth omission (also fixed) and the low-severity "Field label/Inline help text" component-row pairing (accepted as-is) round out this list. This file is kept as historical evidence, not as the current state of the spine — read `DESIGN.md`/`EXPERIENCE.md` directly for what's actually true today.

## Overall verdict
The pair is internally consistent (tokens resolve, sources resolve, no broken cross-refs) and appropriately lean for a POC retrofit — but it is thinner than it looks in two ways that matter for a downstream consumer: it documents only one Key Flow, skipping the re-evaluation loop that the PRD calls the product's actual point, and it has drifted from the shipped code in a few concrete spots (a documented "no side-by-side" layout rule that the code contradicts, a chip claimed as a pill that isn't styled as one, and several real UI states — in-flight progress, both error states, stale analysis — that appear in `app/page.js` but nowhere in EXPERIENCE.md). None of this blocks a competent consumer, but each gap means "trust the spine, don't re-read the code" fails at least once.

## 1. Flow coverage — thin
EXPERIENCE.md declares one Key Flow (Flow 1, lines 72–81), covering steps 1–4 of PRD UJ-1 (arrival → criteria → run-count → Évaluer → Analyser). It has a named protagonist (Camille), numbered steps, a climax beat, and one failure path.
### Findings
- **high** UJ-1 steps 5–6 (`prd.md` lines 42–43: "Julie réécrit son prompt... et relance l'évaluation," explicitly named the "boucle de pratique délibérée" — the PRD's stated learning mechanism) have no Key Flow. The only flow stops right after the first Analyser call; the rewrite-and-re-evaluate loop, and what a second evaluation/analysis cycle looks like (e.g. does `isAnalysisStale` fire, does the chip reset), is undocumented. (EXPERIENCE.md lines 70–81). *Fix:* add a short Flow 2 covering the rewrite → re-evaluate → re-analyze loop, or explicitly note in Foundation why it's out of scope for this pass.
- **low** Flow 1's only failure path is "Analyser clicked before Évaluer" (line 81). No failure path touches the actually-implemented error states (`/api/execute`, `/api/score`, `/api/analyze` failures — all visible in `app/page.js`). Given the doc's own framing ("does not re-derive decisions already fixed by those epics' specs"), this may be a deliberate scope cut rather than a miss. *Fix:* if deliberate, say so in Foundation; if not, add one line acknowledging the inherited abandon-on-error behavior.

## 2. Token completeness — adequate
All frontmatter tokens (7 colors, 3 typography roles, 3 rounded values, 3 components) are defined; every `{colors.x}` / `{rounded.x}` / `{typography.x}` reference in the Components section resolves. Hex values match `app/globals.css` exactly (verified `--primary: #851f6b`, `--accent: #d99a2b`, etc.).
### Findings
- **medium** No contrast ratios are stated anywhere in DESIGN.md, yet EXPERIENCE.md's Accessibility Floor explicitly delegates to it: "Visual contrast lives in `DESIGN.md` (existing app tokens; not re-audited as part of this pass)" (EXPERIENCE.md line 64). The delegation target has nothing to inherit — accent-on-cream and accent-on-accent/15 (used for the "à clarifier" status and every chip) are exactly the load-bearing combinations that need a stated ratio or an explicit "not verified" flag. *Fix:* add one line to DESIGN.md Colors stating either the ratios or that they're unverified for this POC.
- **low** The app uses a systematic opacity scale on `foreground`/`primary`/`accent` (`/10, /15, /30, /40, /50, /60, /70, /80` — visible throughout `app/page.js`, e.g. lines 251, 336, 469, 546) to encode text hierarchy (primary text vs. muted vs. disabled). DESIGN.md documents only one such reference (`{colors.accent}/15` on the chip). The opacity scale itself is a real, reused design decision that isn't captured as a token or convention anywhere. *Fix:* one sentence in Colors naming the opacity convention, even without full enumeration.

## 3. Component coverage — thin
Four components in DESIGN.md.Components (primary-button, secondary-button, chip, status pill); four in EXPERIENCE.md.Component Patterns (field label, inline help text, count/ratio chip, Évaluer/Analyser buttons).
### Findings
- **high** DESIGN.md's "Status pill (analysis dimensions)" (line 84) has no counterpart row in EXPERIENCE.md.Component Patterns — no behavioral spec at all (does it update live, is it static once analysis returns, does it change on re-analysis of an edited prompt?). Every other visually-specified component has a matching behavior row; this one doesn't. *Fix:* add a Component Patterns row for the status pill.
- **medium** EXPERIENCE.md's Component Patterns row for "Count/ratio chip" (line 46) states all three chip uses — "Criteria count, run count, per-criterion stability" — are rendered as "Monospace, accent-tinted pill." Checked against `app/page.js` line 488, the per-criterion stability ratio (`{passedCount} / {totalRuns}`) is plain `font-mono text-accent` text with no background, no padding, no `rounded-full` — it is not styled as a pill, unlike the criteria-count and run-count chips (lines 291, 316) which are. The spine's claim doesn't match the shipped app for this specific instance. *Fix:* either restyle the stability ratio as a pill to match the claim, or correct the EXPERIENCE.md row to note it's plain text, not a pill.
- **low** "Field label" and "Inline help text" (EXPERIENCE.md lines 44–45) have behavioral rows but no dedicated visual-spec row in DESIGN.md.Components — their visual spec is only inferable from the Typography section (line 64) and generic body-copy rules. Workable, but not the clean 1:1 pairing the other two components get. *Fix:* low priority; either add stub rows or accept as an intentional simplification for trivial cases.

## 4. State coverage — thin
Sole IA surface: "Main screen." EXPERIENCE.md's State Patterns table (lines 49–56) lists 4 states: empty criteria, slider at N=1, slider at N>1, neither action clickable.
### Findings
- **medium** In-flight progress states (`isRunning` / `isAnalyzing`) are real, visible states — the `aria-live` progress text ("exécution 2/5", "analyse en cours…") — but appear only as an aside in Accessibility Floor (line 67), not as rows in State Patterns. *Fix:* add rows for "evaluation in progress" and "analysis in progress."
- **medium** Both error states (`error` from a failed evaluation, `analysisError` from a failed analysis — both rendered as `role="alert"` panels in `app/page.js` lines 385–401) are absent from State Patterns entirely, and not mentioned anywhere else in EXPERIENCE.md. *Fix:* add an error-state row, even a short one noting it's inherited/unchanged from Epic 1–2.
- **medium** `isAnalysisStale` ("Prompt modifié depuis cette analyse," `app/page.js` lines 140, 415–419) is a real, currently-shipped state with no mention anywhere in EXPERIENCE.md, despite this pass explicitly touching the Analyser flow and its caption. *Fix:* add a State Patterns row — this is exactly the kind of state this onboarding/clarity pass should own.

## 5. Visual reference coverage — n/a (expected)
`imports/` under this UX folder is empty; no `mockups/` or `wireframes/` directories exist. No orphan or unspecific references to flag — consistent with a retrofit pass on an already-built app with no separate visual-design artifacts produced.

## 6. Bloat & overspecification — strong
Both files are lean. EXPERIENCE.md's Key Flow narration ("she now knows the mechanism... before touching anything") stays tied to specific UI decisions rather than drifting into scene-setting; DESIGN.md's editorial voice ("the tool's own structure looks considered; the user's input stays plain") is scoped to Brand & Style as expected. No pixel values duplicate token values, no restated PRD content found.
### Findings
- **low** Foundation (EXPERIENCE.md line 12) and the file's own blockquote header (line 12, same paragraph) both state the "onboarding/clarity pass on top of Epic 1/2" framing — mildly redundant but harmless.

## Mechanical notes
- Frontmatter `sources` in EXPERIENCE.md resolve: `_bmad-output/planning-artifacts/prds/prd-prompt-evaluator-2026-09-04/prd.md` and `_bmad-output/planning-artifacts/epics.md` both exist.
- Color hex values in DESIGN.md frontmatter match `app/globals.css` exactly (background, foreground, card, primary, primary-hover, accent, border) — no drift between spine and code for the base palette.
- **High-severity mechanical inaccuracy**: DESIGN.md's Layout & Spacing section (lines 68–70) states "Single column... results and analysis render as separate cards below it in the same column — nothing competes side-by-side. This is a form-then-results tool, not a dashboard: sequence, not spatial layout, is the organizing principle." This contradicts `app/page.js` line 421, where the analysis-dimension cards render in a `grid gap-4 sm:grid-cols-2` — genuinely two-column side-by-side on `sm+` viewports. The stated design principle is falsified by the shipped layout. *Fix:* update Layout & Spacing to note the analysis grid's `sm:grid-cols-2` behavior as an explicit, scoped exception, or fix the code if the two-column layout was unintentional.
- DESIGN.md omits an Elevation & Depth section (canonical order: Brand & Style → Colors → Typography → Layout & Spacing → **Elevation & Depth** → Shapes → Components → Do's and Don'ts) even though `shadow-sm` is used pervasively in `app/page.js` (form card, result cards, buttons, alert boxes) and DESIGN.md's own Do's and Don'ts table references shadows ("Nested cards or shadows stacked for fake depth") without the rule ever being stated positively. This reads as an accidental omission rather than a defensible drop — a one-line section ("single flat `shadow-sm`, never stacked, no elevation as a hierarchy device") would close it cheaply.
- No Mermaid diagrams in either file — none needed at this scope.
- DESIGN.md frontmatter omits a `spacing` key (present in the shape example, `design-example-shadcn.md` line 34, even when just noting "inherited, no overrides"). Given no custom spacing tokens exist in this app beyond Tailwind defaults, this is defensible as-is, not a finding.
